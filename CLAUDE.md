# wasafe

Ядро хранения временных диаграмм на C++23: единый хэндл сигнала для скаляров, векторов,
структур и массивов SystemVerilog, единый приём данных из любого формата (`Reader` →
`Builder`) и ленивое чтение по времени и по сигналу из store-файла. Разбор форматов
живёт в отдельных проектах (VCD — `../wasafe-vcd`); ядро о форматах не знает.

- `HANDOFF.md` — источник истины по архитектуре, принятым решениям, статусу и открытым
  вопросам. Отвергнутые решения (§4.9) не предлагать заново без нового довода.
- Спеки и планы — `docs/superpowers/specs/`, `docs/superpowers/plans/`, правила — в
  разделе «Спеки и планы».
- `docs/reviews/ГГГГ-ММ-ДД-<тема>-review.md` — внешние разборы кода на конкретном
  коммите: взгляд со стороны в дополнение к `HANDOFF.md`. Разбор не правится задним
  числом; ссылки на строки в нём относятся к указанному в шапке коммиту.
- `docs/backlog.md` — дефекты и пожелания из проектов, которые используют библиотеку
  (wasafe-vcd, Phosphor). Пункт берётся в работу как задача; закрытый пункт удаляется
  из файла в том же коммите, что и исправление.

## Сборка и тесты

```bash
.venv/bin/conan install . --build=missing -s compiler.cppstd=23 -s build_type=Debug
cmake --preset conan-debug
cmake --build --preset conan-debug
ctest --preset conan-debug --output-on-failure
```

- wasafe — editable-пакет Conan для `../wasafe-vcd` и `../phosphor`: изменение здесь
  сразу видно им, поэтому правка публичного API проверяется и сборкой потребителей.
- Профили: `conan-release` (`-s build_type=Release`), `conan-debug-asan-ubsan`
  (`-pr:a .github/conan/asan-ubsan`), гонки — `-pr:a .github/conan/tsan`. Примеры и
  стенд — `-DWASAFE_BUILD_EXAMPLES=ON -DWASAFE_BUILD_BENCHMARKS=ON`, бинарь
  `wasafe-bench --scale=0.05`; изменения горячего пути (запись store, распаковка
  блоков, курсоры) проверяются им в Release.
- Тесты — один бинарь `wasafe-tests`; файлы перечисляются в `tests/CMakeLists.txt`
  явно, без `file(GLOB)`.
- CI собирает под clang с ASan+UBSan, TSan, clang Release, GCC, MSVC и big-endian s390x
  под qemu, плюс clang-format и clang-tidy по всему дереву и проверку слоёв. Код,
  который раскладывает биты и байты, не должен зависеть от порядка байт хоста.

## Устройство

- Слои, зависимости строго сверху вниз: `io → model → storage → types → core`.
  Нижний слой не включает верхний — это проверяет CI.
- Публичные заголовки — `include/wasafe/<слой>/`, реализация — `src/<слой>/`.
  Экспортируемое помечается `WASAFE_API`.
- Имена целей CMake — через подчёркивание (`wasafe_tests`), alias — `wasafe::<кратко>`,
  имя файла (`OUTPUT_NAME`) — через дефис (`wasafe-tests`).

## Код

- C++23, пространство имён `WaSafe`. Файлы `snake_case`, методы `camelCase`, закрытые
  поля с суффиксом `_`.
- Ошибки — исключением `WaSafe::Exception` (`throw Exception{"..."}`); `std::optional` —
  там, где отсутствие результата не ошибка (`find`).
- Форматирование — `.clang-format`, проверки — `.clang-tidy`; изменённые файлы
  форматируются хуком после каждой правки. Перед тем как показывать результат:

  ```bash
  .claude/scripts/clang-format.sh --check
  .claude/scripts/clang-tidy.sh -p build/Debug
  ```

  Без аргументов скрипты берут файлы, изменённые относительно HEAD; заголовок
  проверяется через `.cpp`, которые его включают. Ожидаемый итог — «формат чист» и
  «замечаний нет».
- Однострочное тело `if`/`else`/`while`/`for` — без фигурных скобок; в цепочке
  `if / else if / else` скобки либо у всех веток, либо ни у одной.
- Вызов конструктора класса — фигурными скобками вместо круглых, где это возможно
  (`ByteReader reader{raw}`, `: raw_{raw}` в списке инициализации). Скаляры,
  константы и `auto` инициализируются присваиванием (`const auto got = f();`).
- В новом коде вместо «bool + out-параметр» — `std::optional<T>`.
- Намеренно отброшенный результат (`[[nodiscard]]`, `cert-err33-c`) —
  `std::ignore = f();`, а не `(void)f();`. Неиспользуемые переменная или параметр —
  `[[maybe_unused]]` на объявлении.
- Строковые литералы в библиотеке, стенде и примерах (`src/`, `include/`, `bench/`,
  `examples/`) — на английском, без кириллицы (сообщения исключений, вывод программ).
- Комментарии на русском, по общим правилам из `~/.claude/CLAUDE.md`.

## Спеки и планы

- Имена файлов: `ГГГГ-ММ-ДД-<тема>-design.md` в `specs/`, `ГГГГ-ММ-ДД-<тема>-plan.md`
  в `plans/`.
- Шапка спеки: дата, статус («черновик на согласование» или «согласовано») и строка
  «Обновлено: …» на каждую правку после согласования. Выбор, который автор спеки
  сделал сам, не обсудив его с пользователем, помечается **[решение спеки]**: так
  видно, что ещё можно оспорить.
- Спека разделяет цели, не-цели и анти-цели. У не-цели сказано, какое ограничение
  она накладывает на архитектуру уже сейчас. Постоянные анти-цели библиотеки —
  замедление горячего пути, память, которая растёт с размером дампа, и знание ядра
  о конкретных форматах.
- Шапка плана: цель, архитектура, ссылка на спеку и раздел **Global Constraints** —
  выдержка из этого файла, которая касается плана, ветка работы и команды сборки и
  тестов. Исполнителю задачи план должен хватать без чтения остального репозитория.
- Следом — **Review Focus**: 3–5 самых рискованных граничных случаев (обрыв store,
  пустая иерархия, предельные размеры, порядок байт) и номер задачи, тест которой
  каждый из них закрывает.
- Задача плана выполняется по TDD: сначала тест и его падение (RED), потом
  реализация (GREEN).
- Принятое по итогам решение заносится в `HANDOFF.md`, чтобы он оставался источником
  истины.
- Рабочие файлы субагентной разработки (`.superpowers/`) в git не попадают.

## Работа по плану и коммиты

- Коммиты делает пользователь. `git add`, `git commit`, `git push` — только по явной
  просьбе на конкретный коммит.
- После каждого пункта плана (а не всего плана) остановиться: прогнать сборку, тесты,
  clang-format и clang-tidy, честно привести результат, включая падения, кратко
  показать сделанное и предложить сообщение коммита в блоке кода. Следующий пункт —
  только после ответа пользователя. Если пункт слишком мелкий для отдельного коммита,
  всё равно остановиться и сказать об этом.
- Агенты-исполнители задач не коммитят и не меняют ветку.
- Ветки `feat/…`, `fix/…` можно заводить без спроса; в `main` напрямую не работать.
- Сообщение коммита: префикс, двоеточие, коротко по-русски без точки в конце.
  Префиксы: `add:` (новое), `fix:` (исправление ошибки или предупреждений), `mod:`
  (изменение поведения), `refactor:` (без изменения поведения), `build:` (сборка,
  зависимости, CI), `doc:` (документация). Тело — только если нужно объяснить «почему».
