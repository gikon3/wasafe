## 1. Цель проекта

Backend-библиотека на **C++23** для хранения и доступа к временным диаграммам
(waveforms) из цифрового моделирования. Требования заказчика:

1. Оформить как **библиотеку**.
2. **Единый интерфейс к сигналам** независимо от типа сигнала и уровня вложенности
   шины (скаляр, вектор, структура, массив — один и тот же API).
3. Поддержка **многомерных массивов и структур SystemVerilog**.
4. **Единый интерфейс записи из любого формата** (VCD, FST и другие) — сам разбор
   форматов вынесен в отдельные проекты, ядро даёт контракт `Reader` + приёмник `Builder`.
5. **Ленивая подгрузка по временным диапазонам и по имени сигнала** прямо из файла,
   без полной загрузки диаграммы в память.
6. Сборка через **CMake + Conan**, стандарт **C++23**.

## 3. Архитектура (слои, зависимости сверху вниз)

```plaintext
io/       Reader (контракт) ─ingest()─► Builder    единый ingestion
storage/  Database ─► Storage                       значения (Memory | Lazy + Index)
model/    Hierarchy / Scope / Signal               структура дизайна + единый хэндл
types/    TypeDescriptor / Value / Logic           типы SV, 4-значная логика
```

Ядро (`src/`) ничего не знает о конкретных форматах — и теперь буквально: реализаций
форматов в репозитории нет. Парсер живёт во внешнем проекте, реализует `Reader` и
подключается пользователем через `ingest()`.

## 4. Ключевые принятые решения

### 4.1 Единый хэндл сигнала (`model/signal.hpp`)

`Signal` — лёгкий невладеющий хэндл `(const Database* db_, NodeId node_)`.
Один и тот же набор методов работает для скаляра, вектора, структуры, объединения,
многомерного массива и любого вложенного элемента/члена:

- структура: `children()`, `child(ordinal)`, `child("name")`, `operator[](i)`, `parent()`;
- значения: `valueAt(t) → Value`, `changes(range) → ValueCursor`, `nextChange`/`prevChange`;
- метаданные: `type()`, `kind()`, `width()`, `isLeaf()`/`isComposite()`, `streamId()`.

Для композита `valueAt` собирает `Aggregate` из детей; для packed-члена —
вырезает срез родительского потока.

`Scope` — аналогичный хэндл узла иерархии-контейнера (модуль/интерфейс/…).

### 4.2 Иерархия (`model/hierarchy.hpp`)

`Hierarchy` владеет `vector<ScopeNode>` и `vector<SignalNode>`; хэндлы ссылаются по
индексу. `SignalNode` может быть листом (`stream` валиден) и/или композитом
(`children`). `BitSlice{offset, width}` (в `std::optional<BitSlice> projection`) описывает, как packed-член
извлекается из потока предка (packed-структуры/массивы хранятся одним вектором).

### 4.3 Система типов (`types/type.hpp`)

Полиморфный `TypeDescriptor`; `Type = shared_ptr<const TypeDescriptor>` (тип
разделяется многими сигналами). Наследники: `ScalarType`, `VectorType`, `ArrayType`,
`StructType`/`Union`, `EnumType`, `RealType`, `StringType`.
**Многомерность массивов выражается вложением**: `logic[7:0] m[0:3][0:1]` =
`Array{0:3, Array{0:1, Vector[7:0]}}`. Безопасный down-cast через `as<T>()`.

### 4.4 Значения (`types/value.hpp`)

- 4-значная логика (`Logic`: 0/1/Z/X) кодируется парой бит-планов **aval/bval**
  (как `s_vpi_vecval`): 0→(0,0),1→(1,0),Z→(0,1),X→(1,1), упакованных в `uint64`.
- `LogicVector` — владеющий; `LogicVectorView` — невладеющий (a*, b*, width).
- `Value` — владеющий `variant<monostate, LogicVector, double, string, Aggregate>`
  (последнее — агрегат struct/array).
- `ValueView` — невладеющий снимок для горячих путей (Logic/Real/String).
- **Контракт времени жизни `ValueView`**: валиден до следующего обращения к backend
  (для `valueAt` — указывает внутрь кэшированного блока, который любое следующее
  обращение может вытеснить из LRU) или до следующего `next()` курсора. Кто хочет
  сохранить — копирует в `Value`; через границу потока вид передавать нельзя по той
  же причине.

### 4.5 Хранилище и backend (`storage/`)

`Storage` — абстракция «откуда значения», оперирует листовыми `SignalId`.
Реализации: `MemoryStorage` (всё в ОЗУ) и `LazyStorage` (файл + индекс блоков).
Сборку композитов из листьев делает уровень выше (`Database`), поэтому
backend одинаков для любого типа листа.

**Потоки — модель shared-nothing.** Экземпляр `Database`/`Storage` после сборки
только читает, но потокобезопасным НЕ является: `LazyStorage` мутирует LRU прямо
в `const`-методах, `FileBlockSource` двигает позицию `ifstream`. Мьютексов в
библиотеке нет ни одного; второму потоку полагается свой экземпляр через
`Database::duplicate()` → `Storage::duplicate()` → `BlockSource::duplicate()`.
Неизменяемое (иерархия, `SignalIndex`, потоки значений `MemoryStorage`, блоки
`MemoryBlockSource`) разделяется через `shared_ptr`, изменяемое (LRU, дескриптор
файла) у дубликата своё. `shared_ptr` наружу не выходит: у `Database` он
приватное поле, публично есть только `hierarchy()` по ссылке.

Следствия для потребителя: `NodeId`/`SignalId` между дубликатами переносимы
(иерархия общая), хэндлы `Signal`/`Scope` — нет (держат указатель на конкретную
`Database`); `ValueView` не владеет данными и через границу потока передаваться
не должен — копируйте в `Value`; `prefetch` греет кэш СВОЕГО экземпляра, поэтому
фоновый поток обязан отдавать наверх готовые значения, а не рассчитывать на
общий LRU.

### 4.6 Единый ingestion (`io/builder.hpp`, `src/io/{base,memory,indexing}_builder.cpp`)

`Builder` — единственный приёмник, через который ВСЕ парсеры наполняют
хранилище. Двухфазный протокол: заголовок (`setTimeScale` / `beginScope` /
`declareVar` / `headerDone`), затем значения (`setTime` / `valueChange` / `finish`).
Реализации: `MemoryBuilder` (в ОЗУ), `IndexingBuilder` (пишет
нормализованный блочный store на диск для последующего ленивого чтения).
Вся общая логика (стек scope, разворачивание композитного `Type` в под-узлы) вынесена
в `BaseBuilder`; наследники переопределяют только `allocStream` / `valueChange` /
`finish` — приёмник значений. **Разворачивание `declareVar`**: лист и packed-композит
получают ОДИН поток (`allocStream`), члены packed-композита — `BitSlice`
с АБСОЛЮТНЫМ смещением внутри этого потока; unpacked-композит не имеет своего потока,
каждый лист-ребёнок получает собственный (для unpacked `declareVar` возвращает
невалидный `SignalId` — единого потока нет).

**Адресация листьев (`leaves`)**: id потоков листьев отдаются наружу через
in/out-параметр `declareVar`. Размер span обязан равняться
`expansionStreamCount(type)` (`types/type.hpp`) — это же правило, что и
`singleStreamRepresentable`, на котором построен `makeStream`, так что источник правды
один. Валидный id на входе привязывает лист к существующему потоку (алиас на уровне
элемента — того, чего нельзя выразить параметром `alias`, работающим только на корне);
невалидный — выделяется и записывается на месте. Размер проверяется ДО первого
изменения состояния, иначе бросок оставил бы builder полуразвёрнутым. Пустой span —
прежнее поведение: порядок разворачивания определён и остаётся гарантией
совместимости, но выводить id счётом выделений больше не обязательно. Вид и ширина
переданного потока не проверяются — симметрично `alias`.

### 4.7 Подключение форматов (`io/reader.hpp`, `io/ingest.hpp`)

`Reader`/`Writer` — контракты для ВНЕШНИХ проектов; в ядре нет ни реестра, ни
детекта формата по сигнатуре, ни `Database::open(path)`. Единственная связка:

```cpp
Vcd::VcdReader reader{"dump.vcd"};                 // проект-формат, выбирает пользователь
auto sink = makeMemoryBuilder();                   // или makeIndexingBuilder(store)
Database db = ingest(reader, *sink);               // read -> finish -> takeDatabase
```

Режим (ОЗУ или ленивый store) задаётся выбранным приёмником, а не флагом. Прошлый
механизм саморегистрации (`ReaderRegistry` + `ReaderRegistration` в статическом
инициализаторе) удалён вместе с его следствием — требованием линковать плагин через
`$<LINK_LIBRARY:WHOLE_ARCHIVE,...>`. Гайд по внешнему проекту-формату:
`docs/writing_a_reader.md`; исходники бывших плагинов VCD/FST — в коммите `955275e`.

### 4.8 Ошибки и id

- Ошибки — исключения: всё, что может провалиться, бросает `WaSafe::Exception` (наследник `std::runtime_error`).
  `std::optional` там, где отсутствие результата не ошибка (`find`/`findScope`).
- Строгие id: `SignalId`, `ScopeId` (шаблон `StrongId<Tag>`), `NodeId`.

### 4.9 Инженерные решения, важные при доработке

- **`StringMap<V>`** (`core/string_map.hpp`) = `unordered_map<string, V,` транспарентный
  хеш`>`. Ключи **владеющие** (иначе `string_view`-ключи висли бы при реаллокации
  векторов узлов), но поиск по `string_view` без аллокации.
- **`SignalChildRange`** итерирует **явный массив `NodeId`** — поэтому один тип
  обслуживает и членов композита (`SignalNode::children`), и сигналы scope
  (`ScopeNode::signals`).
- **`LazyStorage` неперемещаем** (объявлен деструктор из-за pimpl `BlockCache`,
  нет move-ctor) — возврат по значению опирается на гарантированный copy elision (C++17).
- **Push-обход (`visit(range, callback)`) отвергнут** — ни виртуальным методом
  `Storage`, ни свободной функцией. Причины, чтобы не возвращаться: (1) это та же
  развилка pull/push, что уже решена в пользу курсора; (2) `std::function` — косвенный
  вызов на КАЖДОЕ изменение, десятки-сотни миллионов раз за дамп, а шаблонный `visit`
  не виртуален и не проходит границу `WASAFE_API`; (3) `bool`-возврат умеет только
  прервать обход, а GUI нужно «отрисовать сколько влезло в кадр и продолжить с того
  же места»; (4) курсоры композируются (`SliceCursor` поверх `LazyCursor`,
  `MergeCursor` поверх N штук), поверх `visit` слияние не построить; (5) бросок
  пользовательского колбэка посреди обхода обязывал бы реализацию быть
  exception-safe в середине прохода; (6) ещё один обязательный метод для внешних
  реализаций `Storage`. Потребность «обойти все изменения дизайна по времени»
  закрыта пакетным `changes(span<NodeId>)` — скелет в `examples/export_changes.cpp`.
- **`Storage::count(range)` отвергнут** (число изменений без материализации значений,
  чтобы оценить плотность перед децимацией). Точный счёт бесполезен ровно там, где
  нужен: метки времени лежат внутри сжатых блоков, поэтому для `LazyStorage` он
  означает распаковать все пересекающиеся блоки — тот самый I/O, ради экономии
  которого счёт и запрашивали. Грубая оценка уже доступна без единого нового метода:
  `LazyStorage::index()` публичен, а `SignalLocator::blocksIn(range)` отдаёт
  пересекающие блоки с их `time` и `rawSize`. Условие пересмотра — в §7.10.

## 5. Формат блока ленивого backend (СОГЛАШЕНИЯ — критично для IndexingBuilder)

`storage/decoded_block.hpp`:

- `DecodedBlock` — поколоночно (SoA): `times_` отдельно от значений (быстрый бинпоиск).
  Logic: бит-планы `aval`/`bval` лежат **раздельными массивами**, у изменения `i` —
  слова `[i*words, i*words+words)` в каждом, `words = wordsFor(width)`.
  Real: `double[count]`. String: `offsets[count+1]` + арена.
- **`bval` не заводится, пока блок двухзначный** (в нём не встретилось `x`/`z`).
  Первое четырёхзначное значение однократно «повышает» блок, разворачивая план
  нулями под уже записанные изменения. Повышает и значение УЖЕ потока: `append`
  идёт по ширине потока, а биты за шириной значения `LogicVectorView` отдаёт как
  `X`. Условие в обоих `append` поэтому тройное — план заведён, ИЛИ значение
  четырёхзначно, ИЛИ оно уже потока; без третьей ветки запись уходила за границу
  пустого вектора. Наружу это выражено контрактом
  `LogicVectorView`: `bval == nullptr` означает «все b-биты нулевые», поэтому
  зеро-копи сохраняется — вьюха по-прежнему указывает прямо в блок.
- **`times_` — это `TimeColumn`** (`types/time_column.hpp`): база блока плюс
  32-битные смещения, с однократным повышением до абсолютных 64-битных, если
  разность перестала помещаться. Даёт 4 Б на метку вместо 8, сохраняя O(1)
  индексный доступ и O(log n) поиск (`upperBound`/`lowerBound`). Итог по
  раскладке: **12 Б на типичное изменение вместо 24**.
- `encodeBlock`/`decodeBlock` — плоский буфер, magic `'WDB3'`, **явный
  little-endian** через `ByteWriter`/`ByteReader` (`src/core/byte_io.hpp`):
  скаляры собираются сдвигами, массивы на LE-машине уходят одним `memcpy`.
  Заголовок пишется по полям, поэтому раскладка структуры в файл не протекает.
  В заголовке есть байт `flags`,
  бит 0 = `kFlagHasBval`. Метки времени пишутся как zigzag-LEB128 для первой и
  беззнаковые LEB128-дельты дальше; `bval` пишется только при выставленном флаге.
- **Соглашение о блоках** (его обязан соблюдать писатель):
  1. `times` не убывают, только **реальные** изменения (без синтетических переносов);
  2. в каждом блоке **≥ 1 изменение**;
  3. значение в момент t = последнее изменение ≤ t; если t меньше первого изменения
     блока, оно переносится из предыдущего блока (поэтому пункт 2 обязателен —
     `valueAt` делает максимум **один** lookback в предыдущий блок).

`storage/block_source.hpp`: `BlockSource::decode(SignalId, BlockRef) → DecodedBlock` —
единственный метод контракта. Возврат сразу декодированного блока даёт формату со
СВОИМ блочным устройством (FST) читать исходный файл на месте, без круга через нашу
сериализацию; `SignalId` — идентичность потока, нужная там, где один чанк несёт
изменения нескольких потоков.
`storage/raw_block_source.hpp`: `RawBlockSource` — слой для источников, хранящих блоки
в НАШЕЙ сериализации: реализует `decode` через `readBlock(BlockRef) → распакованные
байты`. Наследники — `FileBlockSource` (zstd-распаковка; lz4/zlib — TODO) и
`MemoryBlockSource` (для тестов и store в ОЗУ).
`BlockRef`: `{time, offset, cookie, storedSize, rawSize, codec}`, где `cookie` — 64 бита,
которые ядро НЕ интерпретирует: доадресация блока внутри чанка у чужих форматов.
Ключ LRU-кэша — тройка `(SignalId, offset, cookie)`.

**Соблюдается `IndexingBuilder`** (`src/io/indexing_builder.cpp`), и запись
**потоковая**: каждый поток накапливает не более одного блока, который сжимается
(**zstd**, откат на `Codec::NONE`, если сжатие не уменьшает размер) и уходит в store,
как только набрал `blockChanges` изменений (default 4096). Сверх того действует общий
потолок `bufferBytes` (default 64 МиБ): при его превышении `relieve()` полными
проходами с убывающим порогом сбрасывает самые крупные накопители. Поэтому пик памяти
не зависит ни от размера дампа, ни от числа сигналов, а диаграмма целиком в ОЗУ
не собирается. Оба параметра — в `IndexingOptions`.

⚠️ Два следствия потоковой записи:

- блоки одного потока **НЕ контигуальны во времени**: на момент сброса время
  следующего изменения ещё неизвестно, поэтому `time.end = последнее изменение + 1`
  и между блоками остаются «дыры». Читатель это выдерживает — поиск блока идёт по
  `time.begin` (`blockAtOrBefore`, `blocksIn`), верхняя граница не проверяется;
- блоки **разных потоков чередуются** в файле (раньше блоки одного потока лежали
  подряд), поэтому сканирование одного сигнала стало страйдовым. Восстановление
  порядка требовало бы перезаписи файла и убило бы потоковость.

Store создаётся/усекается уже в конструкторе `IndexingBuilder` — прерванная
ingestion оставляет частичный файл.

## 6. Текущий статус

### ✅ Реализовано (рабочие тела + тесты, 129/129 проходят)

- `core/`: время/диапазоны/масштаб, `Exception`, строгие id, `StringMap`.
- `types/`: 4-значная логика, `LogicVector`/`LogicVectorView` (упаковка, toString, toUint64,
  контракт «`bval == nullptr` — двухзначное значение»), поколоночные срезы
  `ColumnView`/`TimeColumn`, система типов + фабрики + предикаты, `Value`.
- `model/`: `Hierarchy` (построение + `findSignal`/`findScope`/`pathOf` — разбор пути
  по `.`/`[i]`, спуск по scope→signal→member, обратимость `pathOf`↔`findSignal`);
  хэндлы `Signal`/`Scope`.
- `storage/` **ленивый backend — полностью**: формат блока, источники
  (`BlockSource`/`RawBlockSource`, поверх них `File`/`MemoryBlockSource`), LRU-кэш
  с ключом `(SignalId, offset, cookie)`, `valueAt` (+ перенос между блоками),
  потоковый `openCursor` через границы, `nextChange`/`prevChange`, `prefetch`/`release`.
- `storage/` **in-memory путь end-to-end**: `MemoryStorage` (поколоночное хранение,
  `append`/`finalize`/`valueAt`/курсор/`next`/`prev`); `Database::valueAt`
  (агрегат композита из детей, извлечение `BitSlice` из потока предка, материализация
  `ValueView`→`Value`); `MergeCursor` для композитного `changes` + `next/prev` как
  min/max по детям.
- `storage/` **чтение из нескольких потоков (shared-nothing)**: `Database::duplicate()`
  и парные `Storage::duplicate()`/`BlockSource::duplicate()` — по экземпляру на поток,
  без единого мьютекса (см. §4.5). Проверено `tests/test_duplicate.cpp`, в том числе
  под профилем conan `clang-tsan`.
- `storage/`+`io/` **ленивый путь из файла end-to-end**: `IndexingBuilder` —
  **потоковая** запись блоков с потолком памяти (`IndexingOptions{blockChanges,
  bufferBytes}`, см. раздел 5); его `takeDatabase` открывает store через
  `FileBlockSource`+`LazyStorage`.
- **Самодостаточный `*.wsfstore`**: заголовок `'WSF1'` → блоки → метаданные
  (секция `'WSFH'` — иерархия и типы, секция `'WSFI'` — геометрия блоков) → футер
  `'WSFT'` со смещением метаданных и их CRC32 (`src/io/store_layout.hpp`). Файл
  открывается заново через `openStore(path)` без парсера и без исходного дампа;
  спутников у него нет. Сериализацию иерархии и графа типов (с дедупликацией по
  адресу дескриптора) делает внутренний `src/io/hierarchy_codec.hpp`, тело своей
  секции пишет `SignalIndex::encode/decode`, а заголовки секций — слой раскладки.
- **Версии и целостность формата**: версия файла и каждой секции — пара
  major.minor в одном `uint32`. Несовпадение major — отказ; minor больше нашего
  читается вперёд-совместимо, потому что секция несёт свою длину и неизвестный
  хвост пропускается. Отсюда правило: расширять секцию можно только в конец и
  только с приращением minor. Метаданные покрыты CRC32 в футере и проверяются
  всегда — тихое повреждение отличимо от оборванной записи. У блока своя сумма
  (`BlockRef::crc32`), но сверка блоков ВЫКЛЮЧЕНА по умолчанию: замер показал
  удвоение времени ленивого чтения (`RawBlockSource::setVerifyChecksums`,
  `openStore(..., verifyBlocks)`). Ноль в поле означает «не задано» — чужие
  `BlockSource` сумму не считают.
- **Уплотнённая раскладка**: раздельные бит-планы с опусканием `bval` у двухзначных
  блоков + `TimeColumn` (база блока + 32-битные смещения) дают 12 Б на изменение
  вместо 24; на диске метки времени идут LEB128-дельтами, формат блока — `'WDB3'`.
- `io/`: `BaseBuilder`/`MemoryBuilder`/`IndexingBuilder` (см. 4.6) + свободные
  `ingest`/`ingestHeader` (см. 4.7). Оба режима работают: приёмник в ОЗУ либо store
  на диске с ленивым чтением.
- **Форматы вынесены**: `plugins/vcd`, `plugins/fst` и реестр удалены из репозитория
  (VCD-парсер был рабочим — см. коммит `955275e`, если нужен как основа внешнего
  проекта). Тесты и примеры используют синтетические источники (`FakeReader`,
  `DemoReader`), поэтому ядро проверяется целиком без единого форматного проекта.
- Тесты: `test_{logic,types,time,time_column,hierarchy,lazy_backend,memory,indexing,ingest}`.
- Документация: README, 7 UML-диаграмм в `docs/uml/`.

### ⚠️ Ограничения, о которых стоит знать

- **VCD и массивы**: ссылки-элементы вида `mem[3]` сохраняются как ПЛОСКОЕ имя сигнала;
  реконструкция SV-иерархии массива из bit-blasted VCD не делается, поэтому
  `find("top.mem[3]")` их не найдёт (видны только перечислением детей scope). Битовый
  диапазон `data[7:0]` разбирается корректно (имя `data`, вектор нужной ширины).
- **Однопоточность экземпляра**: один `Database`/`Storage` — один поток исполнения
  (`FileBlockSource` двигает позицию `ifstream`, `LazyStorage` мутирует LRU в
  `const`-методах). Это не ограничение библиотеки, а её модель: для второго потока
  есть `Database::duplicate()`, см. §4.5.
- **Оборванная ingestion даёт неоткрываемый файл**: метаданные и футер пишутся
  в `finish()`, поэтому прерванный разбор оставляет store без хвоста. Это видно
  по заголовку и сообщается отдельной ошибкой («store: incomplete»), но
  дочитать такой файл нельзя — только разобрать источник заново.
- **`makeUnion`/`makeEnum` в публичном API нет**: `UNION` и `ENUM` строятся
  прямым `std::make_shared<const StructType/EnumType>(...)`. На сериализацию не
  влияет (кодек зовёт те же конструкторы), но авторам парсеров неудобно.

## 7. Открытые вопросы (требуют решения)

1. ~~**Переносимость формата**~~ → **РЕШЕНО**: и блок, и метаданные пишутся в явном
  little-endian через `ByteWriter`/`ByteReader`; заголовок блока — по полям, без
  раскладки структуры. Остаточный риск: BE-ветка кода на little-endian машине не
  исполняется и даже не инстанцируется, так что проверить её может только сборка
  под big-endian, которой в CI нет.
2. ~~**Семантика `changes()` для композита**~~ → **РЕШЕНО**: merge-курсор отдаёт
  «плоский» поток листовых изменений в хронологическом порядке (`MergeCursor`,
  теперь в `src/storage/merge_cursor.hpp`); `next/prevChange` композита — min/max
  по детям. Агрегат через курсор невыразим (`ValueChange` несёт только листовой
  `ValueView`); снимок-агрегат даёт `valueAt`. **Дополнено**: `ValueChange` несёт
  поле `source` — номер источника, слившего изменение. Для композита это индекс
  листа в `leafNodes(node)`; для `changes(span<NodeId>)` — индекс узла в span.
  Индекс, а не `SignalId`: алиасы VCD дают несколько узлов на один поток, а
  packed-члены одного вектора — одну и ту же проекцию.
3. ~~**Курсор и кэш**~~ → **ИЗМЕРЕНО** (`bench/`, см. §9):
    - **Специализация мультикурсора под последовательный проход по файлу НЕ нужна.**
      Пакетный курсор действительно медленнее N последовательных проходов (при
      N=256 — 404 мс против 87), но ровно тот же разрыв воспроизводится на
      `MemoryStorage`, где блоков нет вовсе (355 против 34). Значит раскладка
      блоков не при чём, и оптимизировать порядок чтения бессмысленно.
    - **`prefetch` для курсоров — холостая работа.** Прогрев 64 потоков стоит
      39 мс и наполняет кэш на 61 МиБ, после чего курсор всё равно распаковывает
      те же блоки сам: он идёт мимо LRU. Учитывать `prefetch` в курсорах не нужно —
      нужно не звать его перед ними.
    - ~~**Настоящее узкое место — компаратор `MergeCursor`.**~~ **СДЕЛАНО.**
      `later()` дважды звал виртуальный `current()` — на каждое выданное изменение
      приходилось ~2·log₂N виртуальных вызовов. Теперь в куче лежит ключ
      `Key{время, источник, подкурсор}`, компаратор чисто арифметический.
      Замер (`--only=cursor --scale=0.15`, до → после): пакетный курсор ускорился
      в 1,3–1,8× (in-memory при N=256: 52,6 → 29,3 мс), контрольные суммы не
      изменились. Разрыв с последовательным чтением сократился, но не исчез
      (in-memory при N=256: 11× → 5,9×) — обещание про «один проход дешевле N»
      по-прежнему давать нельзя.

    Два инварианта, которые эта правка легко ломает:

    1. **Источник перечитывать на КАЖДОЕ заталкивание в кучу, а не кэшировать
       один раз.** У мультипотокового подкурсора (`kKeepSource` — это
       `RemapCursor` из `storage/database.cpp`) `source` меняется от изменения к
       изменению, потому что один такой подкурсор покрывает сразу несколько
       номеров. Закэшированный при построении номер разъедется на первом же
       композите. Ловят `MultiCursor.DatabaseMixedNodes` и
       `MultiCursor.CompositeNumbersDifferBetweenOverloads`.
    2. **Подкурсор нельзя продвигать заранее** — например, ради предвыборки
       следующего ключа. Его `ValueView` живёт лишь до его собственного `next()`,
       поэтому продвижение отложено до начала следующего `next()` кучи (подробнее
       — в шапке `storage/merge_cursor.hpp`). Порядок при совпадении времён держит
       `MultiCursor.TieBreakFollowsRequestOrder`.

    Мерить правку: `wasafe-bench --only=cursor`. Эталон до правки — в числах выше;
    интересна пара `cursor_mem_batch_256` / `cursor_mem_serial_256`, где нет
    влияния блоков.
4. ~~**Политика нарезки `IndexingBuilder`**~~ → **РЕШЕНО, но default под вопросом**:
  замеры показывают компромисс, которого не ожидали: чем крупнее блок, тем меньше
  файл, но тем дороже случайный `valueAt` — промах распаковывает блок целиком.
  256 изменений на блок дают 1.81 мкс на запрос при 3.64 Б/изм, 4096 — 2.75 мкс
  при 3.24 Б/изм. То есть нынешний default покупает 11% диска ценой полуторного
  замедления точечных запросов. Пересмотреть, когда будет известен профиль
  потребителя. Изначально: по числу изменений
  (`blockChanges`, default 4096) плюс общий потолок памяти (`bufferBytes`,
  default 64 МиБ), при превышении которого недозаполненные блоки сбрасываются
  досрочно; кодек zstd с откатом на `NONE`. Оба параметра — в `IndexingOptions`,
  передаваемой в `makeIndexingBuilder`. Можно вернуться к нарезке по
  времени/объёму, если понадобится.
5. ~~**Ленивое открытие форматов**~~ → **КРЮЧКИ В ЯДРЕ ЕСТЬ**: `BlockSource::decode`
  отдаёт `DecodedBlock` напрямую, `SignalId` и `BlockRef::cookie` позволяют адресовать
  блок внутри чужого чанка, а `Database` собирается публичным конструктором из
  `ingestHeader` + своего `Storage` — то есть FST читается на месте, без нормализации
  в `*.wsfstore`. Путь описан в `docs/writing_a_reader.md`, проверен
  `tests/test_foreign_source.cpp`. Остаётся сам FST-reader — он во внешнем проекте.
  Для VCD перегруппировка time-major → signal-major неизбежна: см. разбор в
  `docs/ideas_from_prototypes.md` §3.
6. **Многопоточность**: ~~нужен ли конкурентный доступ к одной БД?~~ (ЗАКРЫТ). Нет: одна
  БД остаётся однопоточной, а конкурентное чтение делается через `Database::duplicate()`
  — по экземпляру на поток (см. §4.5). Разобранная и отвергнутая альтернатива —
  `shared_mutex` вокруг `BlockCache`: он не решает задачу, потому что `valueAt`
  возвращает `ValueView` ВНУТРЬ блока в LRU, и ссылка переживает критическую секцию —
  соседний поток вытеснит блок из-под читателя. Плюс `BlockCache::get` мутирует при
  каждом вызове (splice в MRU), так что читательской блокировки не хватило бы и брать
  пришлось бы всегда write lock. Проверено: `tests/test_duplicate.cpp` под профилем
  `clang-tsan` — чисто, а одна БД на четыре потока даёт гонку в `BlockCache::get`.
  Замеры `value_at`/`cursor` до и после совпадают: на горячем пути не появилось ни
  атомиков, ни блокировок.
7. **Поиск по имени**: точный путь реализован (`Database::find()`), поиска по шаблону
  нет — объявлявший его `SignalQuery` убран, потому что три его метода из четырёх БД
  закрыла сама (`leafNodes()`, `changes(span)`, `storage().prefetch()`), а четвёртый
  так и не был реализован. Что решено на будущее, чтобы не проходить разбор заново:
  - **форма** — свободные функции в `model/` поверх публичного `Scope::scopes()`/
    `signals()` (прецедент — `ingest()`), а не класс-запрос: состояния у него нет,
    приватные части БД ему не нужны, а `Database` не должна разрастаться тем, что
    выражается через её же публичный API;
  - **объём задаёт GUI, и пары «шаблон + предикат» ему мало**: нужен поиск на любой
    глубине (фильтр «показать всё, где есть `clk`» — `*` через `.` не переходит), флаг
    регистра, поиск scope'ов для дерева модулей и обход с ранним выходом (лимит
    результатов, отмена на большом дизайне). Пока такого потребителя нет,
    проектировать вслепую не нужно;
  - **классы символов `[a-z]` в шаблон брать нельзя**: скобки в путях заняты индексами
    массивов, иначе `regs[*]` неоднозначен, а строку из `fullPath()` пришлось бы
    экранировать перед подстановкой обратно в шаблон. Метасимволы — только `*` и `?`.
  (ещё открыт)
8. ~~**CMake-пакет**~~ → **РЕШЕНО**: под опцией `WASAFE_INSTALL` ставится не только
  `install(EXPORT wasafe-targets)`, но и сгенерированный из
  `cmake/wasafe-config.cmake.in` пакет (`configure_package_config_file` +
  `write_basic_package_version_file`), поэтому `find_package(wasafe CONFIG)`
  работает и без Conan (`src/CMakeLists.txt`).
9. **Массивы в bit-blasted источниках**: нужна ли реконструкция SV-иерархии массивов
  (`mem[3]` → элемент узла `mem`)? Сейчас такие имена остаются плоскими. Вопрос
  в основном к проектам-форматам. (открыт)
10. **Заменить собственный формат хранения существующим** (главный вопрос по storage):
  `*.wsfstore` — самодельный. Критерии: блочная подгрузка по времени и по сигналу,
  хранение иерархии и типов, сжатие, переносимость между машинами/ABI. Кандидаты на
  оценку: FST (отраслевой waveform-формат), Arrow IPC/Parquet (колоночные — `DecodedBlock`
  и так SoA), HDF5. **Больше ничего не блокирует**: переоткрытие сделано, порядок
  байт починен. Кодек иерархии и типов при смене контейнера не пропадает — SV-модель
  (packed-структуры, многомерные массивы, enum'ы, битовые проекции) в плоский список
  переменных FST не ложится, описывать её придётся самим при любом исходе; меняется
  только то, в какой файл лягут эти байты. (ОТКРЫТ)
  **Что стоит прицепить к этой правке, когда она случится**: поле `BlockRef::count`
  (число изменений в блоке). Сейчас его нет, а добавление ради него одного ломает формат
  (`src/io/store.cpp` бракует чужой major наглухо — все существующие `*.wsfstore`
  перестали бы открываться). При смене формата по другой причине поле достаётся
  бесплатно и закрывает оценку плотности без распаковки (см. отвергнутый `count(range)`
  в §4.9). Оговорка: для внешних `BlockSource` (сценарий FST) это новая обязанность,
  а счёт они знают не всегда.
11. **Эргономика `ValueChange::source`**: у мультикурсора `source` — это индекс
  в векторе, переданном в `changes()`, поэтому вызывающий держит вектор рядом и
  пишет `nodes[cur->source]`. Рассмотрено и **отложено** (на 2026-08-24): в обоих
  реальных сценариях индекс и есть то, что нужно, — прямая индексация своего
  параллельного массива (`idents[cur->source]` у экспортёра, `rows[cur->source]`
  у GUI), без поиска по `SignalId`. Когда появится потребитель, которому неудобно:
    - **делать через `ValueCursor`** — `node()`/`signal()` на пользовательской
      обёртке, которая создаётся один раз на запрос: она запоминает `const Database*`
      и копию вектора узлов, `ValueChange` не меняется, горячий путь не дорожает.
      Цена — новый `src/storage/value_cursor.cpp` и (только для `signal()`)
      forward-декларация `Signal` в storage-заголовке;
    - **НЕ делать методом на `ValueChange`**: он рождается в storage-слое, который
      про `Database` не знает, поэтому ссылку на запрос заполнить некому. Пришлось
      бы либо оборачивать переходником быстрый путь (`database.cpp`, ветка «все узлы
      простые» — сейчас курсор storage отдаётся без единой обёртки), либо заводить
      сеттер в интерфейсе `Cursor`, обязательный и для внешних реализаций. Плюс
      48 → 56 байт с копированием на каждое изменение в `MergeCursor::next()`.
12. **Ожидание и объём нормализации time-major источников (VCD)**: три рычага, ни один
  не сделан. (ОТКРЫТ, до первого потребителя)

    Предпосылка, которую важно не потерять: **перегруппировка неизбежна, и это вывод,
    а не недоделка**. VCD устроен time-major («момент → кто изменился»), а нужный GUI
    доступ — signal-major («изменения этого сигнала на этом отрезке»). Чтобы отдать
    один сигнал на диапазоне, из time-major придётся распарсить на нём ВСЕХ, поэтому
    «прокрутить один сигнал по всему дампу» вырождается в чтение всего файла на каждый
    запрос. `*.wsfstore` — плата именно за разворот time-major → signal-major, а не за
    ленивость. Универсального «ленивого доступа без нормализации» не существует в
    принципе: `Reader` — интерфейс ОДНОНАПРАВЛЕННОГО проталкивания (`read(Builder&)`
    идёт от начала до конца, ни `seek`, ни входа в середину), а `BlockSource` —
    интерфейс ПРОИЗВОЛЬНОГО доступа. Из forward-only push нельзя изготовить
    random-access pull, не сохранив то, что проехало мимо, а сохранённое с индексом по
    времени и потокам и ЕСТЬ store. Расширение контракта не спасает: `seekable()` +
    `readFrom(checkpoint, …)` реализуем не всяким форматом (gzip'нутый VCD, потоковый
    ввод), а войдя в середину, не знаешь текущих значений сигналов, которые в этом окне
    не менялись, — нужен снимок всех сигналов на каждый чекпоинт, то есть опять
    хранение данных под другим именем.

    Убрать можно не проход, а ожидание и объём:

    1. **Отложить.** Сейчас `ingest()` — всё или ничего. Открытие могло бы делать
       только `ingestHeader()` (он для этого и заведён): дерево сигналов появляется
       мгновенно, нормализация стартует в фоне при первом запросе значений. Примитив
       есть, фонового запуска нет — это скорее сторона потребителя, чем ядра.
    2. **Сузить.** GUI показывает 50 сигналов из 200 000, а нормализуются все. Builder
       с whitelist'ом потоков отбрасывал бы `valueChange` для остальных прямо на входе:
       `makeIndexingBuilder(store, {.streams = visible})`. Проход по файлу тот же, объём
       материализованного падает на три-четыре порядка. Тонкость: добавили сигнал в
       окно — нужен новый проход, поэтому материализованное имеет смысл накапливать
       инкрементально, а не пересобирать. Сейчас `IndexingOptions` знает только
       `blockChanges` и `bufferBytes`.
    3. **Не на диск.** Те же блоки и тот же zstd, только поверх `MemoryBlockSource`
       вместо `FileBlockSource` — третий режим рядом с двумя существующими,
       `makeIndexingBuilder()` без пути. По цифрам §9 это ~3,24 Б на изменение против
       ~12 Б у `MemoryStorage`, то есть вчетверо меньше RSS, и ни одного файла на диске.
       Правки в `src/io/indexing_builder.cpp` невелики: `flushStream` пишет не в `out_`,
       а в `MemoryBlockSource::put`; заголовок и хвост файла в этом режиме не нужны
       вовсе. Стало привлекательнее после появления `duplicate()`: `MemoryBlockSource`
       разделяет карту блоков, поэтому такая целиком-в-ОЗУ ленивая БД размножается по
       потокам бесплатно — дубликату достаётся свой LRU, сами блоки не копируются.

    Приоритет: третий рычаг самый дешёвый и ложится на готовое; второй даёт главный
    выигрыш по объёму, но требует продумать инкрементальное дополнение; первый — в
    основном на стороне GUI.

    Сводка по источникам — нужен ли второй файл на диске:

    | источник | второй файл | чем берётся |
    | --- | --- | --- |
    | FST и прочие signal-major со своим индексом | не нужен | свой `BlockSource` над исходным файлом + `SignalIndex` из нативного индекса (сделано, см. `docs/writing_a_reader.md`) |
    | VCD, влезающий в ОЗУ в сжатом виде | не нужен | нормализация в `MemoryBlockSource` (рычаг 3) |
    | VCD, не влезающий | нужен | перегруппировка неизбежна, это плата за signal-major доступ |
    | произвольный `Reader`, «без материализации вообще» | — | невозможно: `Reader` однонаправлен и одноразов |

3. **Выбрать формат хранения** (§7.10) — теперь ничего не блокирует, и есть с чем
   сравнивать: 3,24 Б на изменение и 3,7 млн изм/с на запись (§9).
4. **Мелочи качества**: `toSvString` (полная SV-нотация типов — улучшит вывод

   ОЗУ и whitelist потоков (§7.12) — по мере появления реальной потребности.

## 9. Замеры (`bench/`)

Отдельный исполняемый файл, по умолчанию не собирается:

```bash
cmake -B build/Release -DWASAFE_BUILD_BENCHMARKS=ON
./build/Release/bin/wasafe-bench            # таблица для чтения
./build/Release/bin/wasafe-bench --csv      # машиночитаемо
./build/Release/bin/wasafe-bench --only=cursor --scale=0.25
```

Синтетический дамп детерминирован: 1024 потока, 200 000 тиков, ~5,2 млн
изменений. Смесь как в настоящих дампах — 2% сигналов с периодом 2 дают больше
половины всех изменений. Полный прогон ~11 с.

Опорные цифры (Release, x86-64, тёплый page cache):

| величина | значение |
| --- | --- |
| разбор в ОЗУ | 4,05 млн изм/с |
| разбор в store | 3,73 млн изм/с |
| размер на диске | 3,24 Б на изменение (zstd) |
| открытие готового store | 0,24 мс |
| проход курсором, один поток | ~0,35 мс на 10 тыс. изменений |
| случайный `valueAt`, кэш 256 МиБ | 1,57 мкс |
| случайный `valueAt`, кэш 1 МиБ | 16,7 мкс |
| ведение курсора по 64 сигналам | 0,41 мкс на запрос |

**Оговорка о достоверности**: дамп (16 МиБ) целиком помещается в page cache, то
есть замеры отражают процессорную стоимость, а не дисковую. Вопросы про
ввод-вывод (в том числе исходная формулировка §7.3) этим стендом не проверяются —
для них нужен store заметно больше ОЗУ.
