# wasafe — backend для хранения временных диаграмм

[![CI](https://github.com/gikon3/wasafe/actions/workflows/ci.yml/badge.svg?branch=main&event=push)](https://github.com/gikon3/wasafe/actions/workflows/ci.yml)

Библиотека на C++23 для хранения и доступа к временным диаграммам (waveforms)
из цифрового моделирования. Даёт **единый интерфейс к сигналам** независимо от
их типа и уровня вложенности, поддерживает **структуры и многомерные массивы
SystemVerilog**, **единый интерфейс записи из любого формата** и **ленивую
подгрузку по временным диапазонам и именам** без полной загрузки диаграммы
в память.

**Чтение конкретных форматов (VCD, FST, …) в этот проект не входит.** Библиотека
определяет контракт [`Reader`](include/wasafe/io/reader.hpp); парсеры живут в
отдельных проектах, а какой из них использовать — решает пользователь, передавая
его в [`ingest()`](include/wasafe/io/ingest.hpp). Ни реестра форматов, ни
автоопределения по сигнатуре в ядре нет — см. [docs/writing_a_reader.md](docs/writing_a_reader.md).

> Статус: **работает end-to-end**. Конвейер «Reader → нормализованный store →
> ленивый или in-memory доступ» покрыт модульными тестами (GoogleTest); прогон
> в CI на каждый push: Debug под ASan/UBSan и под TSan, Release с примерами и
> стендом, сборки GCC и MSVC, `clang-tidy`, `clang-format` и прогон под s390x,
> то есть на big-endian. Незакрытые места помечены
> `TODO(impl)` — их четыре, все локальные (см. [Что не доделано](#что-не-доделано)).

## Как закрыты требования

| Требование | Решение |
| --- | --- |
| Единый интерфейс к сигналам вне зависимости от типа и вложенности шины | [`Signal`](include/wasafe/model/signal.hpp) — один лёгкий хэндл для скаляра, шины, структуры, объединения и элемента массива. Те же методы `valueAt`/`changes`/`children`/`operator[]` на любом уровне. |
| Многомерные массивы и структуры из SV | Система типов [`type.hpp`](include/wasafe/types/type.hpp): `StructType`, `ArrayType` (многомерность — через вложение массивов), `EnumType`, `VectorType`. Packed-члены описываются битовыми срезами родительского потока (`BitSlice` в [hierarchy.hpp](include/wasafe/model/hierarchy.hpp)). |
| Общий интерфейс записи из любого формата | [`Builder`](include/wasafe/io/builder.hpp) — единый приёмник ingestion. Любой [`Reader`](include/wasafe/io/reader.hpp) (VCD/FST/…, реализуется вне этого проекта) пишет только через него и ничего не знает о хранилище; связка — [`ingest(reader, sink)`](include/wasafe/io/ingest.hpp). |
| Доступ по диапазонам времени или имени сигнала в файл, динамическая подгрузка без полной загрузки в память | [`Storage`](include/wasafe/storage/storage.hpp) + [`LazyStorage`](include/wasafe/storage/lazy_storage.hpp) + [`SignalIndex`](include/wasafe/storage/signal_index.hpp): в памяти только метаданные и индекс блоков; значения тянутся блоками по запросу `changes(range)` / `valueAt`. Поиск по имени — [`Database::find`](include/wasafe/model/database.hpp). Готовый `*.wsfstore` самодостаточен и переоткрывается [`openStore(path)`](include/wasafe/io/store.hpp) без исходного дампа и без парсера. |
| C++23, CMake + Conan | `std::span`, `std::print`, ranges, `std::variant`. Стандарт требует сама цель — `target_compile_features(wasafe PUBLIC cxx_std_23)`; рецепт дополнительно проверяет профиль через `check_min_cppstd(23)`, поэтому `-s compiler.cppstd=23` обязателен (по умолчанию в профиле 20). Сборка через [`conanfile.py`](conanfile.py) + [`CMakeLists.txt`](CMakeLists.txt); при `WASAFE_INSTALL` генерируется и `wasafe-config.cmake`, так что `find_package(wasafe CONFIG)` работает и без Conan. |

Модель ошибок — **исключения**: всё, что может провалиться, бросает
[`WaSafe::Exception`](include/wasafe/core/exception.hpp) (наследник
`std::runtime_error`). Кодов возврата и `std::expected` в API нет; `std::optional`
используется там, где отсутствие результата — не ошибка (`find`/`findScope`).

## Архитектура

Слои зависят только «сверху вниз»; ядро не знает о конкретных форматах.

```plaintext
   внешние      ┌────────────────────────────────────────────────┐
   проекты      │ Reader (VCD, FST, …) — реализуют контракт ядра │
                └───────────────────────┬────────────────────────┘
                                        │ ingest(reader, sink)
                ┌───────────────────────▼──────────────────────┐
   io/          │ Builder (MemoryBuilder | IndexingBuilder)    │  единый ingestion
                └───────────────────────┬──────────────────────┘
                                        ▼
   model/       ┌────────────────────────┐   ┌──────────────────┐  storage/
                │   Database             │──►│  Storage         │  значения
                │ (иерархия + значения)  │   │  ├ MemoryStorage │
                │                        │   │  └ LazyStorage   │◄─ SignalIndex (блоки)
                │ Hierarchy / Scope /    │   └──────────────────┘
                │ Signal (единый хэндл)  │  структура дизайна
                └────────────┬───────────┘
   types/       ┌────────────┴──────────────────────────┐
                │ TypeDescriptor, Value, Logic          │  типы SV (4-зн. логика)
   core/        └─ time / exception / ids / string_map ─┘  базовые типы
```

### Единый интерфейс сигнала

`Signal` одинаков для всего. Композит (struct/array) раскрывается через те же
`children()` / `child(name)` / `operator[]`, а доступ к значению (`valueAt`,
`changes`) единообразен — для композита значение собирается из листьев.

```cpp
WaSafe::Signal s = *db.find("top.cpu.regs[3].ctrl");   // любой уровень вложенности

s.type();                       // дескриптор SV-типа
s.valueAt(1500);                // значение в момент времени (агрегат для композита)
for (auto field : s.children()) // члены структуры / элементы массива — те же Signal
    use(field.name(), field.valueAt(1500));

auto cur = s.changes({1000, 2000});  // ленивый курсор по диапазону
while (cur.next())
    use(cur->time, cur->value);
```

### Несколько сигналов за один проход

Отрисовать окно с полусотней сигналов или выгрузить дизайн во внешний формат —
это один курсор вместо N вручную слитых:

```cpp
auto cur = db.changes(nodes, {1000, 2000});   // nodes — вектор NodeId
while (cur.next())
    draw(nodes[cur->source], cur->time, cur->value);
```

Курсор сливает потоки по времени и в `cur->source` сообщает, чьё изменение
отдал, — это индекс в переданном векторе (индекс, а не `SignalId`: алиасы VCD
дают несколько узлов на один поток). При совпадении времени порядок выдачи
следует порядку узлов в запросе.

**Это API про порядок выдачи, а не про скорость.** Оно избавляет от ручного
слияния, но дешевле N последовательных проходов не становится: за общий порядок
платят ~log₂N сравнениями на каждое выданное изменение. По замеру ([bench/](bench),
пара `cursor_mem_batch_256` / `cursor_mem_serial_256`) при 256 источниках
пакетный курсор примерно в шесть раз дороже, чем прочитать те же данные
отдельными курсорами. Берите его там, где нужен хронологический порядок; если порядок не
важен, обходите сигналы по одному.

Вход для экспортёра — `db.leafNodes(db.root().id())`: все листья дизайна обходом
в глубину. Мерджить курсоры листьев вручную не нужно, см.
[examples/export_changes.cpp](examples/export_changes.cpp).

### Ленивая подгрузка

Ленивый режим включается выбором приёмника: `makeIndexingBuilder(store)` пишет
нормализованные блоки (`*.wsfstore`) и индекс, а полученная БД читает их по
запросу. `changes(range)` открывает курсор, который тянет только пересекающиеся
с `range` блоки (`SignalLocator::blocksIn`); `LazyStorage` держит ограниченный
LRU-кэш распакованных блоков (`LazyStorageOptions::cacheBytes`), поддерживает
`prefetch`/`release`.

**Файл самодостаточен.** `*.wsfstore` устроен как заголовок `'WSF1'` → блоки
значений → метаданные (секция иерархии `'WSFH'`, секция геометрии блоков
`'WSFI'`) → футер `'WSFT'` со смещением метаданных и их контрольной суммой.
Спутников — сайдкаров, отдельных индексов — у него нет, поэтому готовый store
открывается заново без парсера и без исходного дампа:

```cpp
WaSafe::Database db = WaSafe::openStore("dump.wsfstore");   // io/store.hpp
auto sig = db.find("top.cpu.pc");
```

**Целостность и версии.** Версия у файла и у каждой секции — пара major.minor:
несовпадение major отвергается, minor больше нашего читается вперёд-совместимо
(секция несёт свою длину, неизвестный хвост пропускается). Метаданные покрыты
CRC32 в футере и проверяются при каждом открытии, поэтому тихое повреждение
файла отличимо от оборванной записи. Значения по умолчанию НЕ проверяются: у
блока своя сумма в индексе, но сверять её на каждом чтении дорого — включается
это третьим аргументом `openStore(path, opts, /*verifyBlocks*/ true)` как режим
«проверь мне файл».

Для форматов без встроенной индексации (VCD) индекс строится за тот же проход и
уезжает в секцию метаданных этого же файла.

**Запись тоже ленивая.** `IndexingBuilder` не собирает диаграмму в ОЗУ: блок
уходит на диск, как только накопил `blockChanges` изменений, а сверх того
действует общий потолок буфера — при его превышении самые крупные накопители
сбрасываются досрочно. Поэтому пиковая память не зависит ни от размера дампа,
ни от числа сигналов, и ограничения на размер обрабатываемого файла нет:

```cpp
auto sink = WaSafe::makeIndexingBuilder(store, {
    .blockChanges = 4096,        // 0 — значение по умолчанию
    .bufferBytes  = 64u << 20,   // потолок накопителей в ОЗУ
});
```

Раскладка блока уплотнена: бит-планы `aval`/`bval` хранятся раздельно, и `bval`
не заводится вовсе, пока в блоке не встретилось `x`/`z` (двухзначные блоки —
подавляющее большинство); метки времени лежат как база блока плюс 32-битные
смещения ([`TimeColumn`](include/wasafe/types/time_column.hpp)) с однократным
повышением до 64-битных, если разность перестала помещаться. На изменение
уходит 12 байт вместо 24. На диске метки дополнительно пишутся LEB128-дельтами.

> Ограничение: метаданные и футер пишутся в `finish()`, поэтому прерванный
> разбор оставляет store без хвоста. Такой файл распознаётся отдельной ошибкой
> («store: incomplete, ingestion did not finish»), но дочитать его нельзя —
> источник придётся разобрать заново.

### Несколько потоков

Собранный `Database` только читает, но потокобезопасным **не является**:
`LazyStorage` мутирует LRU прямо в `const`-методах, а `FileBlockSource` двигает
позицию `ifstream`. Мьютексов в библиотеке нет ни одного — модель
shared-nothing: один экземпляр обслуживает один поток, а второму потоку
полагается свой.

```cpp
WaSafe::Database copy = db.duplicate();   // свой LRU и свой дескриптор файла
std::thread worker{[&] { scan(copy); }};  // иерархия и блоки не копируются
```

Неизменяемое (иерархия, индекс блоков, потоки значений `MemoryStorage`)
разделяется через `shared_ptr`; своё у дубликата только изменяемое — кэш
распакованных блоков и дескриптор файла. Это не копирующий конструктор: файл
открывается заново, LRU начинается пустым, операция стоит дорого — дубликат
заводят на поток, а не на запрос. Формат со своим блочным устройством может
размножения не поддерживать, тогда `duplicate()` бросает исключение.

Что переживает границу потока, а что нет:

- `NodeId` и `SignalId` — **переносимы**: иерархия у дубликатов общая;
- хэндлы `Signal` и `Scope` — **нет**, они держат указатель на конкретную
  `Database`; передавайте `NodeId` и получайте хэндл на месте;
- `ValueView` — **нет**: он не владеет данными и валиден лишь до следующего
  обращения к backend'у. Кто хочет сохранить — копирует в `Value`;
- `prefetch` греет кэш **своего** экземпляра, поэтому фоновый поток обязан
  отдавать наверх готовые значения, а не рассчитывать на общий кэш.

Модель отражена в сигнатурах: `Database::storage()` отдаёт ссылку по
константности самой БД — `const Storage&` из `const Database&` и `Storage&` из
неконстантной. Читающие методы `Storage` константны, поэтому через
`const Database&` доступно всё чтение, а мутирующие кэш подсказки
`prefetch`/`release` требуют неконстантной БД — раздать одну `Database`
нескольким потокам «только на чтение» больше не выглядит безобидным.

### Единый интерфейс записи (ingestion)

Вариант 1 — источником служит парсер формата (из отдельного проекта):

```cpp
Vcd::VcdReader reader{"dump.vcd"};                       // внешний проект-формат
auto sink = WaSafe::makeMemoryBuilder();                 // или makeIndexingBuilder(store)
WaSafe::Database db = WaSafe::ingest(reader, *sink);
```

Вариант 2 — наполнение из своего кода тем же приёмником:

```cpp
auto b = WaSafe::makeMemoryBuilder();
b->setTimeScale({.exponent = -12, .scale = 1});
b->beginScope("top", ScopeKind::MODULE);
auto clk = b->declareVar("clk", makeScalar());
b->declareVar("req", makeStruct({...}, /*packed*/true));  // композит — одним вызовом
b->headerDone();
b->setTime(0);  b->valueChange(clk, ...);
b->finish();
auto db = b->takeDatabase();
```

Любой парсер наполняет хранилище только через `Builder`, поэтому поддержка нового
формата = новый `Reader` в своём проекте, без единой правки в ядре.

## Структура каталогов

```plaintext
include/wasafe/     публичные заголовки (API)
  core/             время, исключения, строгие id, string_map
  types/            логика 4-знач., система типов SV, представление значений,
                    поколоночные срезы (ColumnView, TimeColumn)
  model/            иерархия, Scope, единый Signal, Database
  storage/          storage, индекс блоков, ленивый/in-memory
  io/               Builder, контракт Reader/Writer, ingest(), openStore()
src/                реализация ядра
examples/           dump_hierarchy, query_range, build_inmemory,
                    export_changes (+ DemoReader)
tests/              модульные тесты (GoogleTest)
bench/              wasafe-bench — стенд замеров
docs/               writing_a_reader.md, UML-диаграммы в docs/uml/
```

`Database` объявлена в `wasafe/model/database.hpp`: это фасад над иерархией, а не
хранилище значений, и `Signal`/`Scope` — фасады уже над ней.
Парсеров форматов в дереве нет: они выносятся в отдельные проекты, зависящие от
этой библиотеки ([docs/writing_a_reader.md](docs/writing_a_reader.md)).

## Сборка

Требуется CMake ≥ 3.24, компилятор с C++23 (GCC 14+, Clang 18+, MSVC 19.40+) и Conan 2.

```bash
# зависимости + тулчейн
conan install . --output-folder=build --build=missing \
    -s compiler.cppstd=23 -s build_type=Release

# конфигурация и сборка
cmake --preset conan-release        # пресет создаёт conan
cmake --build --preset conan-release

# тесты
ctest --preset conan-release
```

Опции CMake: `WASAFE_WITH_ZSTD` (ON), `WASAFE_INSTALL` и `WASAFE_BUILD_TESTS`
(ON у верхнеуровневой сборки), `WASAFE_BUILD_EXAMPLES` и
`WASAFE_BUILD_BENCHMARKS` (обе OFF).

Зависимости (через Conan): `zstd` (сжатие блоков ленивого storage), `gtest` (тесты).

CI собирает всё это в контейнере `ghcr.io/gikon3/cpp-arch`
([рецепт](https://github.com/gikon3/ci-images)). Шесть заданий в нём: Debug под
ASan/UBSan, Debug под TSan, Release с `WASAFE_BUILD_EXAMPLES` и
`WASAFE_BUILD_BENCHMARKS` плюс прогон стенда, сборка GCC, `clang-tidy`
по всему `compile_commands.json` и `clang-format` по всем исходникам.

Седьмое — MSVC на `windows-2022`, без контейнера.

Восьмое — **сборка и тесты под s390x**, единственная проверка порядка от
старшего к младшему (big-endian). Компиляция нативная (`s390x-linux-gnu-g++` —
обычная x86-программа), под qemu идёт только запуск тестов.

Девятое — **направление зависимостей между слоями**: `grep` по включениям
проверяет, что `core` не тянет `types`, `types` — `model`/`storage`/`io`,
`storage` — `model`/`io`, а `model` — `io`. Контейнер ему не нужен, одна проверка
поверх `checkout`.

Нижняя граница версий из абзаца выше при этом **ничем не проверяется**: образ
несёт свежайшие тулчейны и пересобирается еженедельно, так что CI подтверждает
только их. Сборку на GCC 14 или Clang 18 не гоняет никто.

## Производительность

Замер на синтетическом VCD 2 ГиБ (8 193 сигнала, 77,1 млн изменений), внешний
парсер VCD, i7-12700K, NVMe. Эталон для сравнения — `vcd2fst` из GTKWave 3.3.128,
который решает ту же задачу «дамп → сжатый блочный формат с индексом»:

| | время | пик RSS | артефакт |
| --- | ---: | ---: | ---: |
| wasafe, `makeIndexingBuilder` | 24,3 с | 121 МиБ | 371 МБ (`*.wsfstore`) |
| gtkwave `vcd2fst` | 17,1 с | 152 МиБ | 367 МБ (`*.fst`) |

Пиковая память не растёт с размером входа (55 / 110 / 121 МиБ на дампах
100 МиБ / 500 МиБ / 2 ГиБ) — это следствие потоковой записи и потолка буфера.

Воспроизводимый стенд лежит в дереве — `bench/`, отдельный исполняемый файл,
по умолчанию не собирается:

```bash
cmake -B build/Release -DWASAFE_BUILD_BENCHMARKS=ON
./build/Release/bin/wasafe-bench                      # таблица для чтения
./build/Release/bin/wasafe-bench --only=cursor --csv  # один раздел, машиночитаемо
```

Он гоняет детерминированный синтетический дамп (1024 потока, 200 000 тиков,
~5,2 млн изменений). Опорные числа на Release/x86-64:

| величина | значение |
| --- | --- |
| разбор в store | 3,73 млн изменений/с |
| размер на диске | 3,24 Б на изменение (zstd) |
| открытие готового store | 0,24 мс |
| случайный `valueAt`, кэш 256 МиБ | 1,57 мкс |
| проход курсором по одному потоку | ~0,35 мс на 10 тыс. изменений |
| контрольная сумма (slicing-by-8) | 2,33 ГБ/с |
| сверка блоков при чтении (`--only=verify`) | +15% к обходу курсором |

**Оговорка о достоверности**: этот дамп (16 МиБ) целиком помещается в page
cache, поэтому стенд меряет процессорную стоимость, а не дисковую. Вопросы про
ввод-вывод им не проверяются — для них нужен store заметно больше ОЗУ.
